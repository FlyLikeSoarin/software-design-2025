# Описание deployment-диаграммы

Диаграмма показывает целевую схему развёртывания системы управления дефектами/ремонтом в **prod**: микросервисы в **Kubernetes-кластере**, отдельные **инфраструктурные кластеры данных** (PostgreSQL/OLAP/Kafka/Redis/S3) и **внешние источники/интеграции** (ERP/MES, PLC, IdP/SSO, SMTP).

---

## 1. Узлы и окружения

### Kubernetes Cluster (prod)

Внутри кластера выделены два пула воркеров:

- **Worker Pool: apps x3** - основной пул приложений (масштабирование/репликация сервисов).

  - **API Gateway**
  - **Auth Service**
  - **Defect Service**
  - **Repair Service**
  - **Zone Service**
  - **Crew Service**
  - **QC Service**
  - **Dispatch Service**
  - **Reporting Service**
  - **Notification Service**

- **Worker Pool: jobs** - фоновые задания.
  - **Report CronJobs (ETL/агрегации)**

Также в кластере присутствует:

- **Ingress Controller** - входная точка для внешнего HTTP-трафика в кластер.

### Data/Infra clusters

Отдельный слой инфраструктуры данных:

- **PostgreSQL (HA) x3** - основная транзакционная БД.
- **OLAP (ClickHouse/Timescale)** - хранилище для аналитики/отчётности/агрегаций.
- **Kafka x3** - шина событий.
- **Redis Cluster x3** - кэш/очереди/оперативные состояния диспетчеризации.
- **S3 Object Storage** - объектное хранилище для файлов (например, отчёты/экспорты).

### External

Внешние системы и каналы:

- **ERP/MES** - источник производственных событий/данных.
- **PLC Events** - события от оборудования/линии.
- **IdP / SSO** - внешняя система аутентификации.
- **SMTP** - отправка уведомлений по email.

---

## 2. Входной трафик и API

1. Внешние запросы приходят в **Ingress Controller**.
2. Ingress проксирует трафик в **API Gateway**.
3. Gateway маршрутизирует запросы на доменные сервисы:
   - `Gateway → Defect/Repair/Zones/Crew/QC/Dispatch/Reporting/Notification`

---

## 3. Аутентификация

- **API Gateway → Auth Service → IdP/SSO**  
  Gateway делегирует проверку/получение токенов сервису авторизации, который интегрируется с внешним провайдером (SSO).

---

## 4. Хранение данных и роли хранилищ

### Транзакционные данные

- Доменные сервисы пишут/читают данные из **PostgreSQL (HA)**:
  - `Gateway → Defect → PG`
  - `Gateway → Repair → PG`
  - `Gateway → Zones → PG`
  - `Gateway → Crew → PG`
  - `Gateway → QC → PG`

### Диспетчеризация и оперативные состояния

- **Dispatch Service** использует **Redis Cluster**:
  - `Gateway → Dispatch → Redis`  
    (например, очереди, быстрые статусы, блокировки, временные слоты/назначения)

### Аналитика и отчётность

- **Reporting Service** работает с **OLAP**:
  - `Gateway → Reporting → OLAP`
- **Report CronJobs** выполняют ETL/агрегации и также пишут в OLAP:
  - `CronJobs → OLAP`

### Файлы и выгрузки

- **Reporting Service → S3**  
  (например, генерация отчётов/экспортов в виде файлов)

---

## 5. Событийная интеграция (Kafka)

Сервисы публикуют события в **Kafka**:

- `Defect → Kafka`
- `Repair → Kafka`
- `QC → Kafka`

Это позволяет:

- строить асинхронные интеграции,
- разгружать синхронный API,
- питать аналитический контур/потоки обработки событий.

---

## 6. Интеграции с производством (MES/PLC)

Внешние источники данных напрямую передают события в доменные сервисы:

- `ERP/MES → Defect`
- `ERP/MES → Repair`
- `PLC Events → Defect`
- `PLC Events → QC`

---

## 7. Уведомления

- `Gateway → Notification Service → SMTP`  
  Сервис уведомлений отвечает за доставку сообщений (email) через внешний SMTP.

---

## 8. Идея масштабирования и отказоустойчивости (по подписи диаграммы)

- Приложения развёрнуты в Kubernetes, **apps x3** подразумевает репликацию/горизонтальное масштабирование.
- Инфраструктурные компоненты имеют кластерность: **PostgreSQL HA x3**, **Kafka x3**, **Redis x3**.
- OLAP и S3 выделены отдельно как специализированные хранилища для аналитики и файлов.
